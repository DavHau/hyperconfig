## Q1 — Current state of CPU KV offloading

**Flags.** `--kv-offloading-size <float GiB>` (CacheConfig.kv_offloading_size; "When TP > 1, this is the total buffer size summed across all TP ranks" — i.e. per engine instance, so two co-hosted engines each set their own) plus `--kv-offloading-backend {native|lmcache}` (default `native`). `VllmConfig._post_init_kv_transfer_config` (vllm/config/vllm.py:867-903) translates native → `kv_connector="OffloadingConnector"`, `kv_role="kv_both"`, `kv_connector_extra_config.cpu_bytes_to_use = GiB<<30`. Env `VLLM_USE_SIMPLE_KV_OFFLOAD=1` (default 0, envs.py:2004) swaps in `SimpleCPUOffloadConnector` — avoid it (open cross-stream-sync corruption #47282; #45704 was the store-side twin). `--kv-offloading-backend lmcache` → `LMCacheMPConnector` — broken on Qwen3.5/3.6 hybrids (open #45407 "External KV connector is not verified yet" crash). Full control alternative: `--kv-transfer-config` JSON; extra-config keys (docs/features/kv_offloading_usage.md): `cpu_bytes_to_use` (required, bytes, total across workers), `blocks_per_chunk` (default 1) or `block_size` (tokens; mutually exclusive; avoid `block_size` — open #48919 startup assert when an EAGLE/MTP draft KV group has a different GPU block size), `eviction_policy` `lru`(default)|`arc`, `store_threshold` (min lookups before offload-eligible, default 0), `offload_prompt_only` (default **True** — decode blocks NOT offloaded by default; base.py:524-526), `spec_name` (`CPUOffloadingSpec` default → plain pinned-CPU tier; `TieringOffloadingSpec` adds fs/obj/p2p secondary tiers).

**Connector implementation.** `vllm/distributed/kv_transfer/kv_connector/v1/offloading_connector.py` (scheduler/worker split in `offloading/{scheduler,worker}.py`), medium framework in `vllm/v1/kv_offload/` (`cpu/manager.py` = block pool + LRU/ARC policy, `cpu/gpu_worker.py` = async `cudaMemcpyAsync` DMA into pinned host memory). Connector prefers cross-layer KV blocks and requires HND layout.

**Hybrid GDN coverage: yes, per-group, including mamba state.** Every KV-cache group is offloaded, including `MambaSpec` groups (worker.py:124-127 byte-views the GDN state pages). Mamba groups are treated as sliding-window-of-1-chunk ("Mamba depends on a single state", scheduler.py:106-108): only the final state chunk of each alignment segment is store-reachable, and hits require `mamba_cache_mode="align"` — the hit window is rounded down to the mamba chunk alignment (`resolve_mamba_align_size`, scheduler.py:134-151). Hybrid models MUST run with `--enable-prefix-caching` (config.py:54-57 assert). Hybrid support landed via #41445 (2026-05); it is not a full-attention-only feature anymore.

**Eviction/promotion flow: an extra prefix-cache tier + preemption restore, NOT mid-request VRAM spill.** Stores are write-behind: as chunks (`blocks_per_chunk` GPU blocks) complete during prefill (and decode iff `offload_prompt_only:false`), async D2H copies are queued; content-addressed by block hash (`make_offload_key(block_hash, group_idx)`). Lookup happens at request admission (`get_num_new_matched_tokens` → `_lookup`); hits are promoted asynchronously (returns `(num_hit_tokens, True)`) into freshly allocated GPU blocks. CPU-side eviction is LRU (default) or ARC at `prepare_store` time; a full pool skips the store (never blocks/fails the request). Running requests' working set stays entirely in VRAM — GPU capacity still bounds concurrency; the CPU tier saves recompute after GPU prefix-cache eviction and restores preempted requests (`handle_preemptions`). MTP interaction: `SpeculativeConfig.use_eagle()` returns True for method `"mtp"` (speculative.py:1324-1328), which marks all groups `is_eagle_group` → the volatile trailing chunk (draft-layer KV of last accepted position, rewritable after spec rejection) is excluded from store during decode and popped during lookup (invariant from #44784, repaired by #46972).

## Q2 — The three tracked fixes + newer bugs

Ground truth on the release branch: v0.26.0 forked from main at dcfebf93f (2026-07-20 04:17Z) + 12 cherry-picks (none KV-offload-related).

Hit-rate fix (outputs were already correct). **First release: v0.26.0** (GitHub compare v0.25.1...3354dba38 = "diverged" → not in v0.25.x; v0.26.0...3354dba38 = "behind" → contained). - **#49071** "Propagate EAGLE mode to SimpleCPU coordinator" (9bc266d92, merged 2026-07-20 06:39Z — 2h22m AFTER the fork): 6-line fix in `vllm/v1/simple_kv_offload/manager.py` (`use_eagle=False` hardcoded → derive from speculative_config). **Only affects `SimpleCPUOffloadConnector`** (VLLM_USE_SIMPLE_KV_OFFLOAD=1). **In no release; main only.** Irrelevant if you stay on the default OffloadingConnector.

- **Newer bugs since 2026-05 (offload ± spec decode), still open unless noted:**
  - **#49127 (OPEN, filed 2026-07-19, THE blocker):** native KV offloading + prefix caching on Qwen3.6 silently changes the interpretation of an identical request after a long shared-prefix request cycles the tier (20/20 tools → 16/20, deterministic, same missing positions; no MTP needed; `--kv-offloading-size 16`, fp8 KV in repro). Maintainer could not repro at 500k padding on main@7a98c7a (2026-07-22) but the reporter reproduced at 600k on the same commit — trigger tracks cache/offload pressure, not length. Unfixed on main as of 2026-07-23.
  - **#49118 → fix #49146** (merged 2026-07-21, **NOT in v0.26.0**): aborting a queued never-scheduled (or preempted) request → `assert len(offload_keys) == len(offload_chunk_ids)` in `_build_store_jobs` → EngineCore death. Reachable from a mere client disconnect while the queue is busy. The enabling change #48596 ("Offload last block at request finish", f38f3d11) **IS in v0.26.0**, so **v0.26.0 is exposed**. For coding-agent traffic (frequent client aborts) this alone disqualifies offload on v0.26.0.
  - **#48959 → fix #49052** (merged 2026-07-26, NOT in v0.26.0): unaligned sliding-window external load can intersect window+1 GPU blocks → assert in `update_state_after_alloc` → EngineCore death. Trigger geometry needs a true token-window SWA group (DeepSeek-V4-class); Qwen3.6 GDN hybrids have full-attn + mamba(window=1) groups, so likely not directly exposed, but it's the same load-path invariant family.
  - **#48919 (OPEN):** extra-config `block_size` + spec decode → startup assert when the draft group's GPU block size differs ("all groups must have the same block size"). Use `blocks_per_chunk`, never `block_size`.
  - **#49226** "Disable cross-layer KV blocks for per-token-head quant" (48ebd6f2f, merged 2026-07-26, NOT in v0.26.0): cross-layer connector layout corrupts KV under per-token-head quant dtypes (`fp8_per_token_head`/`int8_per_token_head`/`int4_per_token_head`); plain `fp8`/`fp8_e4m3` is FP8_PER_TENSOR (kv_cache_interface.py:62-74) and NOT affected.
  - Tiering/P2P-only (not applicable to CPU-only): #49902 (unilateral promotion floods DRAM tier), #49829 (HIT_PENDING has no deadline → requests defer to client timeout), #49820, #49809. Simple-connector-only: #47282. DSpark-only: #47890.

## Q3 — expandable_segments vs offloading connector

Still mutually exclusive, by explicit startup rejection: `VllmConfig._verify_kv_transfer_compat` (vllm/config/vllm.py:903-939; present in the v0.26.0 tag at :901-925) raises ValueError whenever ANY `kv_connector` is configured and `PYTORCH_CUDA_ALLOC_CONF` contains `expandable_segments:True`. Rationale: PyTorch's VMM allocator can remap KV virtual addresses to different physical pages, invalidating pinned/registered KV memory; vLLM "can't enumerate every connector that pins memory, so we conservatively reject the combination whenever any KV connector is configured." **Sanctioned escape hatch:** `--enable-cumem-allocator` (in v0.26.0; ModelConfig.enable_cumem_allocator, auto-enabled by sleep mode) — `CuMemAllocator.use_memory_pool` toggles `expandable_segments` off around its pool (device_allocator/cumem.py:333-370, ref #40812) so the KV cache lands on stable physical pages while the rest of the process keeps expandable segments. Perf implication of just dropping the env var: you lose VMM-backed defragmentation, i.e. higher long-run fragmentation-OOM risk — relevant for two co-hosted engines with tight `gpu-memory-utilization` budgets. Recommendation: keep `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` and add `--enable-cumem-allocator` to both engines when enabling offload; fall back to dropping the env var only if cumem misbehaves.

## Q4 — fp8 KV (#40756 / PR #48475)

**Not fixed anywhere. PR #48475 is still OPEN** (state OPEN, labels bug + needs-rebase, last update 2026-07-19) — it clamps `i_t = num_accepted_tokens-1` to ≥0 in `fused_recurrent_gated_delta_rule_fwd_kernel` / `fused_sigmoid_gating_delta_rule_update_kernel`; the author explicitly calls it "defense-in-depth rather than a confirmed root-cause fix". No merged commit references it; no release contains any fix for this class. Issues #40756 and #41190 remain OPEN. The definitive account is brasrox's 2026-07-19 comment on #40756: deterministic ≤3-round repro on RTX 5090 sm_120, v0.25.1 AND nightly main 2026-07-18 (so v0.26.0 is equally affected), Qwen3.6-27B NVFP4 + hybrid GDN + MTP n=6 + `--kv-cache-dtype fp8_e4m3` + 2-way concurrency. Root cause: a stale/discarded batch row reaches the GDN metadata with `num_accepted_tokens==0` → `i_t=-1` → OOB read of `ssm_state_indices` → garbage-positive state pointer → cudaErrorIllegalAddress (first fault often in `_causal_conv1d_update_kernel`, which consumes the same offset). #47466 (in v0.25.0/v0.26.0) does not address it. The builder clamp (`gdn_attn.py`: `num_accepted_tokens.clamp_(1, num_spec+1)`) + #48475 kernel clamps survive 20/20 stress rounds including a CPU-offload-at-100% soak with byte-identical greedy output — but the reporter's own caveat matches yours: the clamp converts the crash into a silent write to stale rows; if those `spec_state_indices` slots were reallocated to a live request, that is cross-request state corruption instead of an IMA. Corroborating: fuzz549 (2026-07-10) — "bf16 kv runs stable, even with mtp"; every Blackwell + MTP + FP8-KV combination fails his benchmark. **Verdict: fp8 KV for the 27B stays blocked; keep bf16 KV.** fp8-KV+offload interplay is therefore moot; note the one open offload-corruption issue (#49127) used fp8 KV in its repro config, and #49226 (main-only) fixed a distinct connector-corruption for per-token-head quant dtypes only.

- **fp8 KV, 27B: still blocked** (no merged fix; open PR is a clamp with silent-corruption risk; bf16-KV is the known-stable configuration).

**Flags when you adopt (per engine; TP=1 so sizes are whole-engine):**
- 27B: `--kv-offloading-size 36` — 36GiB ≈ 1.1× its 32GiB GPU pool (CPU chunk bytes = total GPU-KV bytes per block incl. mamba pages × blocks_per_chunk, so CPU token capacity ≈ (36/32)× the GPU pool's token capacity). Docs: a CPU tier smaller than the GPU pool "just mirrors what the GPU already holds and adds no hit rate" — treat 36 as the floor, 40 if RAM allows.
- 35B: `--kv-offloading-size 12` — 3× its 4GiB pool.
- Total 48GiB pinned host memory (allocated up-front) out of ~60GiB idle → ~12GiB headroom; verify `free -g` with both engines up before load.
- Both engines additionally: `--kv-transfer-config '{"kv_connector":"OffloadingConnector","kv_role":"kv_both","kv_connector_extra_config":{"offload_prompt_only":false,"eviction_policy":"arc"}}'` (`_post_init_kv_transfer_config` merges `cpu_bytes_to_use` from `--kv-offloading-size` into this). `offload_prompt_only:false` because agent turns' decode output becomes the next turn's prefix; `arc` for scan-resistance under agent churn (optional; `lru` default is fine). Do NOT set `block_size` (avoid #48919); leave `blocks_per_chunk` default 1.
- Keep `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` and add `--enable-cumem-allocator`, or drop the env var (Q3).
- Keep `--kv-cache-dtype` at bf16/auto. Never set `VLLM_USE_SIMPLE_KV_OFFLOAD` or `--kv-offloading-backend lmcache`.

**Ordered validation checklist (prove MTP-with-offload correctness):**
1. Boot: no expandable_segments ValueError; logs show `Creating offloading spec with name: CPUOffloadingSpec` and `KV offloading: EAGLE/MTP draft attention groups [...] detected`; host pinned RSS grew by cpu_bytes_to_use.
2. Greedy determinism A/B: ≥50 deterministic requests (temperature=0, fixed seed + cache_salt, mix of short and 100k+ prompts), engine with offload OFF vs ON, MTP ON in both. Completions must be byte-identical.
3. Restore correctness: prime a > GPU-pool prefix, churn the GPU cache until evicted, resend the identical request; `External prefix cache hit rate` > 0, TTFT collapses, and the greedy continuation is token-identical to a fresh-prefill baseline (this is #46972's own acceptance test).
4. #49127 probe: run the tool-visibility gist (A → B → A with deterministic tools) with B's padding scaled past cpu_bytes_to_use so the CPU tier actually cycles; both A responses must be identical. Repeat at 2-4 padding sizes. Any divergence = do not ship.
5. Abort-storm (#49118 regression): fill the queue past `--max-num-seqs` with >1-block prompts, abort queued clients (1s timeouts), 3 rounds; engine must stay alive and answer afterward.
6. MTP-under-offload soak: 4-8 concurrent low-acceptance (free prose) generations mixed with offload restores at tier ≈100% for ≥1h; SpecDecoding metrics must match the no-offload baseline (acceptance length, per-position rates); `scheduled_spec_decode_tokens=[-1,...]` or a sudden 100% acceptance rate is the #40756 pre-crash signature — abort trial.
7. Preemption path: shrink GPU pool or burst load to force preemptions; resumed requests must produce valid (baseline-matching) output.
8. Multi-day burn: watch offload Prometheus gauges (CPU cache usage %, allocation-size histogram, allocation failures), EngineCore restart count = 0, no host swap.

## Breaking changes
- v0.26.0 contains #48596 (final-block store on request finish) without its follow-up #49146: aborting a queued never-scheduled request with OffloadingConnector active kills EngineCore (assert in _build_store_jobs). Any offload deployment on v0.26.0 is one client disconnect away from a full-engine outage.
- Enabling any KV connector (including --kv-offloading-size) now hard-rejects PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True at startup unless --enable-cumem-allocator is set — your current env var must change when offload is enabled.
- offload_prompt_only defaults to True: decode-generated blocks are NOT offloaded unless you set offload_prompt_only:false in kv_connector_extra_config — silently halves multi-turn agent hit rates if left default.

## Caveats
- #49127 is OPEN and reproduces on main (2026-07-23): native offload + prefix caching on Qwen3.6 can silently restore a wrong prefix under cache pressure (identical request returns different tool visibility). No fix exists on any branch; gate adoption on the local A→B→A probe regardless of which tag you run.
- The three tracked fixes have split fates: #46972 IS in v0.26.0 (first release); #49071 (Simple connector only) and #49671 (tiering-manager crash; default CPU manager not exposed) are main-only and irrelevant to the default single-CPU-tier path you would run.
- fp8 KV + MTP + hybrid GDN on sm_120 remains an unfixed crash class (#40756/#41190 open; PR #48475 open/needs-rebase; clamp workarounds trade the crash for silent cross-request state-corruption risk). bf16 KV is the known-stable configuration (fuzz549, 2026-07-10).
- Do not set kv_connector_extra_config block_size with MTP (startup assert #48919 when the draft KV group's block size differs); use blocks_per_chunk. Avoid VLLM_USE_SIMPLE_KV_OFFLOAD (#47282 corruption) and lmcache backend on hybrids (#45407).
- Tiering/P2P secondary tiers carry additional open bugs (#49902 promotion floods DRAM, #49829 HIT_PENDING has no deadline, #49820/#49809) — stay on the default CPUOffloadingSpec (no secondary_tiers).
- FlashInfer sm_120 MoE workspace/autotune memory is not fully accounted during profiling (#49476/#49115, still present on 2026-07-21 nightly with FlashInfer 0.6.14) — keep VRAM headroom margin for the 35B MoE engine when re-tuning gpu-memory-utilization.
- MTP acceptance decays with total context length on dense Qwen3.6-27B (#47602, all draft positions, not just tail) — monitor per-position acceptance at your real context distribution; n=2 is less exposed than the reported n=6.
- cpu_bytes_to_use is pinned (page-locked) host memory allocated at startup: 36+12 GiB across the two engines out of ~60GiB idle leaves ~12GiB; verify no swap with both engines loaded before adding load.
